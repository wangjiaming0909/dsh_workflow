# v0.1.3 — DSH 0.2.0-rc.2 compatibility

## Feature_004: Load and run on the DSH 0.2.0-rc.2 release

### Problem

The plugin could not be loaded into `dsh 0.2.0-rc.2` at all. DSH evaluates a plugin bundle's `@deepseek-ai/dsh*` peer ranges against the running runtime before mounting it; every peer still pinned `^0.0.1-rc.2`, which no `0.2.0-rc.2` runtime satisfies, so the profile bundle was refused and reported as `skipping profile bundle "@dsh-external/workflow"`. Even past that gate, the plugin called Session, message, and job APIs that no longer exist in `0.2.0-rc.2`, and its build and test configuration resolved DSH packages through hardcoded `../test-icetomoyo` snapshot paths.

### Contract

- Every `@deepseek-ai/dsh*` peer range admits the running runtime (`^0.2.0-rc.2`), and `@deepseek-ai/dsh-tool-workflow` — whose event payload types the engine imports — is a declared peer and development dependency.
- `compatibility.json` records the verified runtime: `https://github.com/deepseek-ai/deepseek-harness.git`, ref `dsh-v0.2.0-rc.2`, commit `639ed015397290b3745d163aafe02ffee4aa3f84`, version `0.2.0-rc.2`; the default snapshot directory everywhere is `../deepseek-harness`, still overridable with `DSH_SNAPSHOT_DIR`.
- Child Agent logs are read through `Session.snapshotEvents()`. Successful tool evidence comes from `ToolResultMessage.toolCallId` and `ToolResultMessage.isError`, because the `tool-result` content block no longer exists in the message vocabulary.
- The plugin declares its own merge-extensible message source kind, `dsh-external-workflow`, for the authoring contract, live `wf.send` messages, and verification repair prompts; DSH removed the shared catch-all `plugin` kind.
- Background workflow jobs are owned by the Agent's `SessionId` (`Agent.id`), matching `JobSpec.owner`.
- Session-scoped `tool-workflow/run-start` events keep carrying explicit Session ownership (`turn: null`), which the `0.2.0-rc.2` Conversation location index still honours, so a background run stays `running` after its launching step and turn close.
- DSH packages resolve through their published `exports` from installed dependencies; no build or test configuration embeds a snapshot file path.

### Trade-off

`Session.snapshotEvents()` is marked `@deprecated` in `0.2.0-rc.2` in favour of projections and explicit paged history reads. Reconstructing a child Agent's token usage and tool evidence needs the child's own log, and DSH exposes no projection key for that fact set, so the plugin keeps the synchronous reader — the same reader the removed `Session.events` getter already implied. If DSH removes the three synchronous readers, child usage accounting and evidence verification must move to an explicit asynchronous historical read.

### Verification

- `dsh plugin --profile web add <plugin>` installs the bundle without an incompatibility diagnostic, and `dsh --profile web --dump-config` composes the `dsh-external-workflow` layer.
- Booting the real `dsh 0.2.0-rc.2` web profile with the bundle reports no `skipping profile bundle`, and an in-profile probe confirms the plugin's `dynamicWorkflows` service is mounted.
- `pnpm check` passes end to end: compatibility pin, real-DSH Conversation projection check (`turn: null` keeps a session-scoped run `running` across step and turn closure, and the matching `run-end` alone settles it), 179 tests, typecheck, and build.
- The command-lifecycle regression now asserts the generated Session title is derived from the preserved human message's exact seq, not from the relayed authoring context.
